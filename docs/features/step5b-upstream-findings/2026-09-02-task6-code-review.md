## Summary

The contract module reads exactly as section 12 and 13 promise: the reviewer report validates the canonical identity plus the reviewer's own severity/classification/subject with an upstream token checked per artifact, the reconciliation validator refuses structural errors by name and converts content failures (`unmatched grounding`, `extra/duplicated/omitted normative claims`) to `cannot_determine` with the author's rationale retained and the failure noted, and the names say what the checks prove — textual occurrence, never logical support. The stages run the phase order panel → reconciliation → gate once per legacy pass, rerun the mechanical gates on the reconciled artifact before writing it, and retain the before/after hashes on a machine-readable event. The duplicated stage wiring and the duplicated per-prompt assertions are the plan's own pattern.

Two findings, both in the layer that turns the contract into model behaviour rather than in the contract itself: the reconciliation prompts advertise a fixed example `findingId` the validator refuses whenever the round's ids do not include 1, and the base harness fixtures emit the same normative claim from every decision, so the happy path silently carries a converted decision that no test observes. Withheld: the legacy severity gate still deciding the run is Task 9's stated transition, not a finding; the whole-file source scan's inability to localize a sentence carried by two prompts is the documented reason the per-prompt tests exist; and style observations.

## Findings

**Finding 1 — the reconciliation prompts advertise a fixed example findingId the validator refuses**

- **Where:** `reconciliationDecisionContract`'s example envelope in `src/prompts.ts`, rendered by both `buildSpecReconcilePrompt` and `buildPlanReconcilePrompt`: `"decisions": [{"findingId": 1, ...}]`.
- **Why it matters:** Hazard 3's second sentence: every example value a prompt advertises must validate against the schema that receives it. A model that copies the example answers a round whose canonical finding ids do not include 1 — reproduced: against canonical ids `[7]`, the advertised payload is refused with "reconciliation decision names finding 1, which is not a canonical finding of this round". A model that copies the example's id for each of several findings returns duplicate ids and is refused as `two decisions for finding 1`. The ids are known to the builder, so the example can advertise the first real finding id of the round — the same fix the panel-size example received in Task 5.
- **Reproduced:** `review-repro.mjs` built the prompt with findings `[{findingId: 7}]` and confirmed the example contains `"findingId": 1` while `validateReconciliation` refuses findingId 1 against ids `[7]`. (The scratch file was deleted after the review.)

**Finding 2 — the base harness fixtures give every decision the same normative claim, so the happy path silently carries a converted decision**

- **Where:** `reconcile()` in `test/fixtures/harness/emit-spec-stage.mjs` and `test/fixtures/harness/emit-plan-stage.mjs`: `decisions` is built with `ids.map((id) => ...)` and the same `normativeChanges` entry on every decision, claimed whenever any finding exists — including rounds where the artifact under review is already the revised one and the derived delta is empty.
- **Why it matters:** With two findings and one added node, the second decision's claim is a duplicate and the validator converts it to `cannot_determine`. Reproduced: the fixture's exact payload validates as `1=addressed, 2=cannot_determine`. Every default-fixture run — the happy paths included — therefore records a conversion, and no stage test asserts the happy path's decisions arrived valid, so the conversion is invisible (hazard 4: the fixture and the validator agree, and the agreeing result is never examined). The mixed-pair scratches already claim once, on `index === 0`; the base fixtures should claim once and only when they actually revise, and the happy paths should assert the round-1 reconcile record carries no conversions and no unclaimed nodes.
- **Reproduced:** `review-repro.mjs` ran `validateReconciliation` against the fixture's two-decision payload and observed `conversions: [{findingId: 2, from: "addressed", ...}]`. (The scratch file was deleted after the review.)
