# Implementation Phase Retry Implementation Plan

**Status:** Reconciled

**Goal:** When an implementer's reply for one phase is not valid JSON, dispatch that phase again, at most a frozen number of times per phase and with a prompt that states the refusal, instead of blocking the run at the first refused reply.

**Source:** Operator statements, 2026-10-08. After crew-chatter run 3 blocked at phase 2 of 6 on a malformed reply, the operator asked whether run 4 should wait for a fix; given four options (report both parse errors, accept the failures, retry, change what a reply carries) the operator answered "Lets go with the retry." Evidence: crew-chatter run 3 phase 2 ($0.7790 for the refused reply, $6.4623978 recorded for a run that reached one committed phase), recorded in `test/fixtures/recorded/crew-chatter-run-3-phase-2-malformed-json.json` (written, uncommitted); and a 2026-10-08 scan of every retained raw reply on this machine, in which 3 of 20 file-carrying replies failed the strict parse (team-notes run 9 phase 2, crew-chatter run 2 phase 2 and crew-chatter run 3 phase 2; the extractor's repair rescued the second and not the third). The scan is written up in `.claude/sessions/project-learnings.md`. My recommendation to the operator that day said "retry the same phase once" and did not mention `ARCHITECTURE.md` section 19 and hazard 7, which forbid a retry that resends an identical prompt. This plan keeps the operator's choice and obeys that rule by varying the prompt.

**Assumptions:**
- **"The retry" means one more dispatch of the same phase, so a phase may use at most two dispatches.** That is my reading, not a stated number. It is one frozen policy value, `implementationPhaseAttempts`, seeded at 2; 1 turns the retry off and restores today's behaviour exactly, down to the text of the refusal. A ceiling of 3 is enforced when a frozen profile is loaded (operator decision, 2026-10-09), so a mistaken constant cannot multiply paid dispatches without bound: attempts repeat spend on a repeated failure, where phases only bound the work.
- **Only a reply that is not valid JSON is retried (operator decision, 2026-10-09):** the `extractJsonBody` call in `src/implementation-stage.ts` returned `refused` and the reason contains ` is not valid JSON: `, the wording `src/parse-output.ts` gives both refusals that carry a `JSON.parse` message (the fenced-block form and the unfenced form). At that point nothing has been applied, the worktree has just been checked clean, and the cause is the measured one (a model lapsing out of JSON escaping late in a long reply). In the 2026-10-08 scan of 189 retained replies the extractor refuses 6: five are API-error replies that fail at dispatch before any parse, and the sixth is crew-chatter run 3, the only retained reply that reaches the parse and is refused. No prose-only or two-block phase reply has been recorded. Not retried, because each has a different cause or a different consequence: the extractor's other refusals (`expected exactly one JSON block, found N` and `no JSON object found in output`), which the escaping notice does not address; a dispatch failure (a usage-limit refusal, a timeout, a non-zero exit); a dirty worktree after the dispatch; a reply that parses but fails `validateAgentResult`; a status other than `proposed`; an empty patch list; and any patch-application refusal. The stage keys on that wording, which couples it to `src/parse-output.ts` without changing it; Task 4's tests pin both sides of the coupling.
- **The first attempt's prompt states the double-quote rule (operator decision, 2026-10-09).** `buildImplementationAuthorPrompt` gains one sentence beside the line-break rule, so the rule the recorded failure broke is in the prompt that requests the field (hazard 3). That changes the prompt every first attempt of every new run receives, for an effect nobody has measured. The retry prompt is still that prompt byte for byte, plus the notice. The code-review remediation prompt carries its own copy of the escaping paragraph and is not changed (Open decision 3).
- **The retry comes after the extractor's existing repair and changes nothing in `src/parse-output.ts`.** A reply the repair can fix never reaches the retry (crew-chatter run 2 phase 2 was such a reply).
- **The variation is the prompt.** The retry prompt is the original phase prompt, byte for byte, followed by a notice that states the attempt number, the parser's reason, that nothing from the earlier reply was applied, and the two escaping rules the recorded failure broke. Model and effort do not change: the `implementer` is one frozen setting, and a second setting would be a second schema.
- **Every attempt is a normal successful dispatch**, so it writes its own `agent_run` row and its own raw file, and its cost is counted like any other. No cost is hidden.
- **Nothing resumes.** The phase repeats inside the same stage execution, before any patch is applied or committed. A run that exhausts its attempts still blocks, with the worktree and earlier commits retained.

**Approach:** Add one frozen policy field, with a ceiling of 3, and an attempt loop around the existing dispatch, clean check and parse in the phase loop. On a refused parse whose reason says the text is not valid JSON, with attempts left, append one audit event, `implementation.phase.retry`, which names the refused attempt's `agent_run` row and the reply's length; build the retry prompt with one new function in `src/prompts.ts`; and dispatch again. Out of attempts, or on any other kind of refusal, abort with the existing `implementation.content.invalid` action and the existing text, plus ` on attempt A of M` once the phase has been retried. The base implementation prompt gains one sentence stating the double-quote rule. The consent preview multiplies the implementation ceiling by the attempts so it does not understate the spend. The fixture emitter learns five modes; the main one replays the recorded malformed reply until it sees a retry prompt, reading the attempt number from the prompt and keeping no counter, so a stage that does not vary its prompt cannot pass. Documents that say "no retry" are corrected in the same change. Rollback is one number: a frozen attempts value of 1 reproduces today's refusal text byte for byte (Task 4 test (d)); only the added sentence in the first prompt differs from today.

## Reading the first paid retry

Operator decision, 2026-10-09. This plan authorizes no paid run. When paid runs happen, each retried phase is read by the rule below, counted across runs in the order they occur. For each retried phase, record three things (the queries are in the runbook row Task 5 adds):

- Whether attempt 2 parsed: the next event for the stage is `implementation.phase.apply`, not `implementation.content.invalid`.
- Whether attempt 2's first error fell in the same file as attempt 1's. Each refusal names a character offset into its reply, and the file is the last `"path"` entry that starts at or before that offset in the saved reply. The recorded run 3 fixture shows the shape: its `provenance.measured.pathKeysAndOffsets` puts offset 54463 inside `backend/src/features/attachments/routes.ts`.
- The length of the reply that was refused, which the retry event carries.

The rule:

- If at least one retried phase parsed on attempt 2, keep `IMPLEMENTATION_PHASE_ATTEMPTS` at 2.
- If two retried phases were refused again in the same file as their first refusal, set the constant to 1, which turns the retry off, and reopen the two options this plan did not choose: reporting both parse errors, and changing what a phase reply carries.
- Anything else changes nothing: no phase retried, one phase refused again, a phase refused again in a different file, or a retried phase that never reached the parse on attempt 2 because of a dispatch failure or a dirty tree. Keep 2 and read again after the next retried phase.

The rule does not settle a mixed history (one phase parsed and two others were refused again in the same file); the operator reads that case. The counts are tiny, so a "keep" reading means the retry has not been disproven, not that it is measured. Task 5 records the rule in the runbook and the learnings file.
