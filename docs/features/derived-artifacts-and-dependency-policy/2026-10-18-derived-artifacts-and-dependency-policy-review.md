## Critical issues — must fix before implementation

**Issue:** 1. The reused cleanup refuses the regenerated lockfile

- **Why it matters:** Task 5 runs `removeIgnoredOutput` after the derived commands and before the derived change is committed. `removeIgnoredOutput` in `src/commit-verification.ts` lists `git status --porcelain -z --untracked-files=all --ignored=matching` and returns `unexpected non-ignored entry …` for any entry that does not start with `!! `. A regenerated `package-lock.json` is a modified tracked file (` M`), so the cleanup refuses it.
- **Where:** Task 5, `regenerateDerivedArtifacts`, the step "Run `removeIgnoredOutput`. A failure returns its reason." placed before the status check and the commit.
- **Production impact:** every phase whose regeneration changes the lockfile blocks with `implementation.derived.failed`. That is exactly the case the plan exists for, so no dependency-adding run can pass. The Task 5 tests do not catch it unless the fixture command also leaves an ignored file.
- **Recommended fix:** reorder Task 5 so that the derived change is checked, staged and committed first, and `removeIgnoredOutput` runs only after the commit, when the tree holds nothing but ignored entries. Then run `checkWorktreeClean`. Add a Task 5 test in which the fixture command changes the derived file and also writes an ignored file, and assert one commit and one cleanup.

## High-risk areas

**Risk:** 2. The remediation prompt has no verification block

- **Why:** the plan says `verificationCommandsBlock` "is already in every author prompt" (Hazards considered, entry 3, and Task 4). In `src/prompts.ts` it is rendered at ten sites, and `buildCodeReviewRemediationPrompt` is not one of them. Task 7 adds its implementation sentence "after their verification block" to three prompts, and the remediation prompt has none, so that placement is undefined.
- **Impact if ignored:** the remediator is never told that `package-lock.json` is regenerated by the system, or that an unlisted package is refused. A remediation that adds a package blocks the run, and so does one that patches the lockfile. These are hazard 21 failures that the plan claims to close.
- **Mitigation:** in Task 4, add the derived-files lines to `buildCodeReviewRemediationPrompt` explicitly, either by rendering `verificationCommandsBlock` there or by a stated insertion point, and name the choice. In Task 7, give the remediation sentence its own insertion point. Correct the hazards line and Task 4's "every author prompt" claim. Add prompt tests for the remediation prompt.

**Risk:** 3. The guided starter keeps the original failure

- **Why:** `README.md` and `CLAUDE.md` call guided mode the primary operator path. `src/project-bootstrap.ts` generates a `static-web` `governed.yaml` with `npm ci` and a committed `package-lock.json`, and the plan leaves that file unchanged ("The starter's generated `governed.yaml` has no `derived:` block and stays valid").
- **Impact if ignored:** a guided project whose design adds a package gets the operator question, the operator approves it, and the run then fails `npm ci` at verification after the plan and every phase have been paid for. That is run 4's predicted failure on the primary path.
- **Mitigation:** decide whether the starter's `governed.yaml` emits the lockfile `derived:` block. `scaffoldSlug` compares a project's committed bytes exactly against `generatedFiles`, so changing the starter means projects bootstrapped before the change are no longer recognized as scaffolded. Under hard rule 3 that is acceptable but must be stated. The alternative is to document that guided projects need the block added by hand. This is an operator decision.

## Medium and low concerns

- **Medium:** the section 23 decision is recorded in Task 10, after Tasks 2–9 build the feature. `CLAUDE.md` requires an explicit decision before building past the milestone. Record the authorization as the first task, and keep Task 10 for the design text.
- **Medium:** Task 8 places the deny branch "after the split's approve branch" but does not say "before any fold dispatch". A fold dispatched for other questions on a run that the deny then blocks wastes one paid call. State that the deny check runs before the fold.
- **Medium:** Task 8's fold refusal compares `dependenciesAdded` lists without saying how. Two lists with the same pairs in a different order must compare equal. State set equality on manifest and name pairs.
- **Medium:** Task 6 excludes derived paths from the `changedPaths` that code reviewers may cite. A reviewer that still cites `package-lock.json` then fails `validateCodeReviewLocations`, and an integrity-failed panel blocks without a review record. Before the change, the same citation ended in a refused remediation. The outcome is no worse, but the plan does not state it, and no test covers it.
- **Medium:** the run command's consent preview prints "Frozen verification commands" (seen in crew-chatter run 4's log), and the plan does not add the derived artifacts to it. The operator then consents to a range without seeing which commands run after every commit. Add them to the preview in `src/operator-output.ts`, and list that file under Blast radius.
- **Medium:** the order inside each phase is stated only in Task 9 ("before regeneration"). Task 6 is built first and says only "after `implementation.phase.apply`". Write the full sequence once in Task 6: apply, audit, dependency check (Task 9), regeneration.
- **Low:** Task 9 parses `package.json` with `JSON.parse`. A manifest saved with a UTF-8 BOM fails to parse and is refused as invalid JSON. Pass the text through `normalizeText` first.
- **Low:** Task 10 updates `docs/runbooks/cli-operator.md` generally. Name the three new refusals (`implementation.derived.failed`, `implementation.dependency.unapproved`, the derived-declaration refusal) for its troubleshooting table.

## Missing and underspecified areas

- The starter decision in finding 3 is missing. The plan needs either a starter change with its `scaffoldSlug` consequence, or a stated operator procedure.
- The remediation prompt's insertion points for both new constraints are missing (finding 2).
- The consent-preview change is missing from Affected areas and Blast radius.

## Suggested improvements

- Record the derived commands' evidence path in the `derived.commit` audit summary, as verification records its evidence references, so a regeneration can be diagnosed from the audit alone.
- Name the regeneration commit's label and base in the code-review record's remediation entry, so a reader can tell the implementer's commit from the system's without opening git.
