## Summary

## Critical issues — must fix before implementation

**Issue: the spec stage admits directory artifact declarations that exact-equality delivery can never honor**

- **Why it matters:** Contract 2 requires every signed artifact path to exactly equal a committed patch path (`plan.md:22-23`). Nothing in the spec pipeline restricts declared artifacts to files: `spec-doc.ts:55-70` validates only that each artifact is non-empty and repo-relative, `computeScope` normalizes and sorts whatever the list holds (`scope.ts:128-140`), and the spec gate re-checks only length and protected paths. A spec declaring `scripts/` or `docs/features/<slug>` passes spec review and is signed today, and a directory entry can never equal a committed path — the run then blocks terminally at the last stage with its full cost spent. The plan's only control is the specification-author prompt clarification (`plan.md:50`), and a prompt instruction is a request, not a rule — the repository's own principle behind section 7's "enforcement belongs in the write path".
- **Where:** Contract 2 (`plan.md:20-24`); the Documentation task (`plan.md:50`); the integration-test list, which covers exact matches, slash normalization, duplicates, extra paths, case mismatches, and missing files but not a directory entry (`plan.md:57-58`).
- **Production impact:** The design's tripwire (hazard 5) fires correctly when a run did not deliver. This makes it fire on a spec that sailed through the spec and plan gates and the operator's signature — a false block at the run's full cost, where the defect is a single line in the spec author's markdown.
- **Recommended fix:** State the file-only invariant as a rule, not a prompt preference: the spec validator refuses a declared artifact that resolves to a directory in the starting tree (new files are the normal case and must stay legal), the author prompt is updated in the same change, and an existing directory declaration refuses by name at the spec gate. Amend `ARCHITECTURE.md` section 12's "appear in the changed paths" wording at the same time — it is prefix-tolerant, which is exactly the ambiguity this issue turns terminal — and add a fixture spec declaring a directory to prove the refusal. This is a deliberate design amendment, not the "clarify" the Documentation task currently calls it; if directory entries stay legal instead, the plan must define delivery matching per entry kind, which weakens the guarantee and should be argued explicitly.

## High-risk areas

**Risk: `patchBaseCommit` has no stated source or capture point, and the two plausible derivations are each wrong**

- **Why:** Contract 1 defines `patchBaseCommit` as "the post-projection commit given to the implementer" and puts it in the gate event, but never says who records it, when, or against what evidence. Today the only durable record of the branch's history is the final head in the gate event's `head=` summary — `verification-stage.ts:142-164` reads it "from that stage's own `implementation.gate.pass` event and nowhere else". The two derivations an implementer could reasonably choose are both wrong: the approval-bound `starting_commit` pre-dates the spec and plan projection commits that land before implementation, so its diff range includes projection changes the plan promises to exclude (`plan.md:32`); the model's claimed `patch.baseCommit` is model output, validated only to equal the head at apply time (`implementation-stage.ts:461-465`).
- **Impact if ignored:** A base captured after any apply, or derived from the approval record, silently re-admits projection-only changes into the changed-path set — the exact failure the gate exists to refuse — while a wrong base derived from model output can block a delivered run. Both fail without any test noticing, because the fixtures and the wrong derivation agree.
- **Mitigation:** State that the implementation stage records the worktree head it read before the first apply — the commit the implementer's patches bind to — as the base, in the same gate event that records the final head. Make the format change and the verification-side parse migration one atomic change: `verification-stage.ts:157` anchors on `/^head=([0-9a-f]{40}|[0-9a-f]{64})$/`, and a new summary shape refuses every post-change run at verification until that parse moves to the shared parser. Add a break-it entry that records the wrong base and confirms a named delivery test fails.

**Risk: "remain clean" at delivery is undefined against untracked files verification commands may leave**

- **Why:** Contract 3 re-checks that the worktree "must exist, remain clean, remain at the verified commit" (`plan.md:31`). Verification commands run in the worktree and nothing contains their filesystem writes — containment is an unbuilt proposal — so a command can leave untracked output. Verification's own exit check watches the head, not dirtiness (`verification-stage.ts:248`); its entry check is porcelain-clean, but that runs before the commands (`verification-stage.ts:180-190`).
- **Impact if ignored:** A porcelain-cleanliness re-check at delivery refuses every run whose frozen verification command emitted any untracked file (test output, a build artifact, a log), at the last stage, after verification already passed it. The delivered artifact is the commits — untracked files are not delivered and cannot be — so the check as written blocks runs whose deliverable is complete.
- **Mitigation:** Define the delivery check as `HEAD` equals the verified commit plus an empty tracked-path diff against it, and say explicitly that untracked files are excluded and why. Add an integration fixture whose verification command leaves an untracked file and assert delivery passes; add the mirrored break-it entry for a tracked modification after verification.

## Medium and low concerns

- The soundness of `git diff --name-only base..HEAD` as "the changed paths of the applied patches" rests on three invariants the plan never states: one anchor, no patch applied after another patch moved a path it touches (the section 7 overlap refusal), and no non-patch system commit between base and HEAD. Contract 1's plural "commits" (`plan.md:15`, `plan.md:36`) invites a multi-commit apply that a later change could implement naively, and a path applied then reverted inside the range disappears from net name-only output. Pin the single-base no-overlap apply, or compute the union of per-commit diffs.
- The plan never orders the stage insert against the terminal transition. Insert-then-transition (`plan.md:26-27`) leaves a crash window in which the run is stranded `in_progress` with a delivery stage that the duplicate-invocation refusal then rejects forever. Verification shares this window today because its commands are long; delivery's work is short — insert the stage and perform the terminal transition in one transaction after the git reads, or state the strand-and-fresh-run repair explicitly.
- The tests name an "invalid approval scope" refusal (`plan.md:63`) that no contract defines. What makes a scope invalid at delivery — an unparseable record, a directory entry (critical issue 1), a path outside the repository? Define it, and state where a directory entry refuses if it stays legal.
- The human-readable report (`plan.md:34`) has no path or name. Name it next to `result.json` so the reference printed on success (`plan.md:42`) points at a real artifact.
- The `ARCHITECTURE.md` section 12 change is an amendment, not a clarification: the section's "appear in the changed paths" sentence is prefix-tolerant, and exact equality is a strengthening. The Documentation task should say what the old sentence allowed that the new one refuses, so the record shows the deliberate change (it is also what makes directory artifacts permanently undeliverable — see critical issue 1).

## Missing and underspecified areas

- The plan names the contracts but not the sites they change: `implementation-stage.ts` gate-event writer (the `head=` summary around lines 418-470), the verification parse at `verification-stage.ts:147-164` and its result writer around lines 290-325, the new delivery module, the `cli.ts` command wiring, and `driver.mjs`'s paid sequence. A task decomposition with per-task verification (the full-path convention this repository's own feature plans follow — `tasks.md` alongside `plan.md`) is the missing executable layer, and the plan carries no `**Status:**` line for the lifecycle the implement-plan skill advances.
- Contract 3's refusal set covers the run and chain preconditions well; it does not cover the two states that need no refusal because they cannot occur — a missing approval row or a non-existent frozen profile — but nothing says what delivery does if the approval record's scope is unreadable while the chain still validates.
- The break-it list (`plan.md:68`) covers exact matching, patch-base diffing, handoff validation, HEAD and cleanliness checks, missing-artifact blocking, and the completed transition — good — but not the verification-parse migration (high-risk area 2), the tracked-vs-untracked definition of clean (high-risk area 3), or the directory-entry refusal (critical issue 1).

## Suggested improvements

- `patchBaseCommit`'s ancestor check (`plan.md:31`) is the right guard against a forged or foreign base; state that it also makes the range comparison well-defined when the worktree history was rewritten.
- Reuse the `implementation.gate.pass` event rather than adding a sibling event for the base, so the two commits stay in one record and the audit summary keeps a single parse site.
- The completed-run CLI boundary exists partially (`requireRunInProgress`); a test that `stage-complete` and the other low-level commands refuse against a completed run closes the boundary for the new terminal value.
