## Summary

The boundary is built carefully. `commitWorkspace` reads the staged diff NUL-delimited with renames off, gates every path of every record, discards derived edits with literal pathspecs before staging, and resets on every refusal. `destroySandbox` proves the work container gone by a successful `rm -f` followed by an `inspect` that reports no such container, and every stage that starts a sandbox checks `workContainerGone` before it reads the worktree. Control calls and command execution are separated as the plan requires, so a failing command is an outcome and an unreadable exit status is a `ContainerError`. Profile freezing covers the whole sandbox, and `invalidProfileReason` refuses a profile without one. The prior design review's eight findings are all present in the code, and none is re-raised here.

The findings cluster on what the containment claim does not cover. The sandbox contains the commands BuildWorks runs, but two host-side paths sit outside it. The system's own `git commit` runs the target's Git hooks on the host after an agent's code has entered the worktree (Finding 1). The tool server's `docker` client inherits a different environment from the stage that created the container (Finding 2). Neither is visible to the suite, because no stage test starts the real tool server and no fixture target has hooks.

Withheld:

- **A nested Git repository is staged as a gitlink (mode `160000`), which `commitWorkspace` does not refuse by mode.** It cannot reach the branch in practice. A gitlink's path is a directory, and a scope entry is a declared file path that `artifactDirectoryRefusals` keeps from naming a directory, so `gatePatchPaths` refuses it as out of scope. The only failure is a block whose reason names the directory rather than the embedded repository, which is speculative hardening.
- **`bw run` does not check the Docker engine before the implementation, verification or code-review group.** A stopped engine there blocks the run terminally after its document stages have spent. A missing `claude` executable at the same point already does the same, because `run` probes neither, so this is a pre-existing pattern the diff extends rather than introduces. Finding 4 covers only the runbook text that describes it.
- **Deliberate decisions and known deviations in the build record**, which were not reported: remediation's base is `currentCommit`; the event `implementation.phase.apply` is kept; link refusal is tested only at the boundary; `self-review-mutate-fail` now skips; the bootstrap `npm` host check and the governed-config `TOKEN` rule are follow-ups; and remediation's quiescence branch has no stage test.
- **Speculative cases with no reachable failure on the supported host:** a `docker run -d` that creates its container and then fails to start leaves a stopped, never-started container that `ids.work` does not hold (it is labelled, and `doctor` lists it), and file ownership by the container's `node` user on a Linux host whose user ID is not 1000.

## Findings

**Finding 1 — The system's host-side `git commit` runs the target's Git hooks on agent-written content, outside every container**

- **Where:** `src/workspace-commit.ts` (`commitWorkspace`, the commit at lines 260-264), and `src/derived-artifacts.ts` (`regenerateDerivedArtifacts`, the commit at lines 232-244), which runs after an agent's change is in `HEAD`. Neither passes `--no-verify` or overrides `core.hooksPath`; no `src/` file does. `ARCHITECTURE.md` section 17 ("Commands are contained") lists what the containment does not cover (the agent session on the host, and package install scripts inside the container) and omits this path.
- **Why it matters:** The plan's guarantee is that agent-authored code runs only inside the work container. A worktree shares the main repository's hooks and `core.hooksPath`. Some targets have a `pre-commit` hook that executes repository content: `core.hooksPath` pointing at a tracked directory, or an installed pre-commit framework or lint step that runs repository scripts or configuration. In such a target, the system's own commit executes the agent's just-gated, in-scope change on the host, as the operator, with BuildWorks' full process environment and file system. That code can read `~/.claude` credentials or an approval key, or write `.governance/state.db`, profiles and audit rows directly. The staged-set and committed-set checks catch only a hook that alters the commit. They do not catch one that acts elsewhere. Hard rule 2 (one mutation authority) and hazard 15's restated guarantee both depend on agent code never running host-side. The configurations that reach this are targets whose hooks run repository content; a target with no hooks, or with hooks that run nothing from the worktree, is not affected.
- **Reproduced:** `C:\Users\tamezs\AppData\Local\Temp\1\claude\C--Repositories-AI-Tools-governed-delivery\8235a81c-d5d8-48c9-94b5-004919f169bf\scratchpad\review-hook-escape.mjs` builds a temporary repository with `core.hooksPath=.githooks` and a tracked `.githooks/pre-commit` that runs `node tool.js`. It replaces the in-scope `tool.js` with code that writes a marker outside the worktree, then calls `commitWorkspace` with scope `["tool.js"]`. The result: `commitWorkspace ok: true [ 'tool.js' ]`, and the marker was written outside the worktree, reading `ran on the host; env names: 116`. No repository file was changed, so nothing needed restoring. The prevention (running host commits with hooks disabled) is a decision for reconciliation.

**Finding 2 — The tool server runs `docker` in the dispatch environment, so it can address a different Docker engine than the stage that created its container**

- **Where:** `src/dispatch.ts` (`dispatchOnce`, `toolServer` at lines 117-127) and `src/harness.ts` (`invokeHarness`: the MCP config at line 294 carries no `env`, and `claude` is spawned at line 320 with `env` from `buildHarnessEnvironment`, the eight-name passthrough). `src/container.ts` (`control`, line 174) and `runVerifyCommand` spawn the stage's Docker client with the full `process.env`, and so do `doctor`'s `docker_engine` and `new-run`'s `dockerReady`.
- **Why it matters:** The Docker CLI selects its engine from `DOCKER_HOST`, `DOCKER_CONTEXT` and `DOCKER_CONFIG`. None of them reaches the tool server. The spike's recorded live session shows the environment the server actually received (`toolServerLog[0].envNames` in `test/fixtures/recorded/sandbox-spike-crew-chatter-phase-2.json`): the harness passthrough plus Claude Code's own variables, and no Docker variable. Consider an operator whose engine is selected through one of those variables, such as Rancher Desktop, Podman, a remote engine or a non-default context exported in the shell. For that operator, `doctor` and `new-run` pass, and the stage creates the sandbox on engine A. Every tool call then targets the default engine and fails with "No such container" or a connection error. The phase spends up to the $2.00 cap, the agent can change nothing, and the run blocks as `blocked` or "changed nothing". This is hazard 9's rule, verify a tool "in the environment that will spawn it", and hazard 12's divergence between two surfaces. The free smoke and every stage test use emitters that write files directly and never start the tool server, so the suite cannot see it.
- **Reproduced (stand-in analogue):** `C:\Users\tamezs\AppData\Local\Temp\1\claude\C--Repositories-AI-Tools-governed-delivery\8235a81c-d5d8-48c9-94b5-004919f169bf\scratchpad\review-env-divergence.mjs` uses the stand-in's state variable `BW_DOCKER_STAND_IN_STATE` in the role `DOCKER_HOST` plays for the real CLI. It creates a sandbox in-process, then calls `run_command` through `src/tool-server.ts` twice. With the full environment the result was `exit code 0`. With `buildHarnessEnvironment(CLAUDE_CODE)` the result was `tool run_command failed: read exit status in 083528a8… failed (docker exit 1): Error response from daemon: No such container`. The real-CLI form was not run, because no engine was used. What would confirm it is one tool call under a non-default `DOCKER_CONTEXT` against a real engine.

**Finding 3 — No stage test reaches `implementation.sandbox.failed` or `code_review.sandbox.failed`, so the plan's start-failure block is unguarded where it blocks a run**

- **Where:** `src/implementation-stage.ts` (`sandboxedDispatch`, the `!run.started` branch) and `src/code-review-stage.ts` (the `!sandboxed.started` branch of remediation). The verification stage's `record === null` start-failure branch in `src/verification-stage.ts` is also covered only below the stage, by `verifyCommit` in `test/commit-verification.test.ts`. A search of `test/` finds `markUnstartable` only in `test/commit-verification.test.ts` and `test/derived-artifacts.test.ts`.
- **Why it matters:** Plan Task 9 step 2 requires that "a `ContainerError` blocks the run with `implementation.sandbox.failed` carrying its message, before any dispatch". The runbook's troubleshooting row, the dashboard and operators read that action by name. A regression could relabel it, drop the message, or let the stage continue past a failed start, and no test would fail. The build record names only the remediation quiescence branch as untested, not this one. That breaks the repository rule "prove a guard by breaking what it guards".
- **Reproduced:** with `breaktest.mjs` (spec `review-bt-sandbox-failed.json` in the scratchpad), the `implementation.sandbox.failed` action was renamed `implementation.author.failed` and `test/implementation-stage.test.ts` plus `test/run-command.test.ts` were run: 88 pass, 0 fail. Then `code_review.sandbox.failed` was renamed `code_review.remediation.failed` and `test/code-review-stage.test.ts` was run: 61 pass, 0 fail. Both files were restored, and their SHA-256 matched the copies (`a78b7219f8d3`, `45906322ddab`).

**Finding 4 — The runbook's `<stage>.sandbox.failed` row implies a run can continue after Docker is repaired, and that the sandbox "could not start" whenever the event appears**

- **Where:** `docs/runbooks/cli-operator.md` line 1072, against `src/implementation-stage.ts` (`sandboxedDispatch`, which calls `abort` and so sets the run `blocked`), `src/code-review-stage.ts` (the `code_review.sandbox.failed` abort), `src/commit-verification.ts` (`runCommands` records `sandbox.failed` for an exit status it cannot read after a command ran) and `src/derived-artifacts.ts` (`runDerivedCommands` does the same after a phase's dispatch has spent).
- **Why it matters:** The row says "Repair Docker from that message" and names a fresh run only for an absent frozen image. Every `sandbox.failed` path blocks the run, though, and `requireRunInProgress` refuses any later stage, so an engine that was stopped when the run resumed after its approval pause leaves no in-place repair. The row's "the sandbox could not start ... nothing was dispatched for that step" is also false for the exec-time cases: `verification.sandbox.failed` after commands ran, and `implementation.sandbox.failed` from derived regeneration after a phase's paid dispatch. An operator following the row repairs Docker and reruns `bw run`, which refuses because the run is `blocked`. The operator then has to work out from the code that a fresh run, re-paying the document stages, is the only recovery (hazard 6).
- **Not reproduced:** read from the row and the four code paths named above. What would confirm it is a stand-in run with `markUnstartable` on the phase prefix followed by a second `run` invocation.

## Reconciliation

Reconciled 2026-10-20 by the implementing session, before the plan was marked `Implemented`. All four findings were accepted after their call paths were traced. Each fix's guard was then broken through `breaktest.mjs` (scratchpad `bt-review.json`): all seven mutations failed their test, and each restore matched by SHA-256.

- **Finding 1: accepted and fixed.** The fix is in `src/workspace-commit.ts`, which now exports `NO_HOOKS` (`-c core.hooksPath=/dev/null`) and prepends it to every call made by its one Git helper. `src/derived-artifacts.ts` prepends it to its own helper. A hooks path that holds no hook disables every hook, including `post-commit` and `reference-transaction`, which `--no-verify` does not. The reviewer's repro now reports `marker written ... false` under Git for Windows. New tests:
  - `test/workspace-commit.test.ts`: "the system's commit runs none of the target's hooks ...";
  - `test/derived-artifacts.test.ts`: "the regeneration commit runs none of the target's hooks ...".

  Each test configures `pre-commit`, `commit-msg`, `post-commit` and `reference-transaction` hooks that run the agent's file. Each keeps a positive control: an ordinary commit fires the same hooks. `src/implementation-stage.ts`'s own Git helper was left alone. Its only commit, the projections commit, and its `worktree add` both run before any agent content exists. Its later calls are read-only diffs and `rev-parse`. The binding text is updated in `ARCHITECTURE.md` section 17, and hazard 15 has a dated 2026-10-20 note.
- **Finding 2: accepted and fixed.** The tool server is spawned under the harness environment, and the reviewer's recorded `envNames` confirm that it holds no Docker variable. Its engine-selection variables are therefore now passed to it by value:
  - `src/container.ts` exports `DOCKER_CLIENT_ENV`: `DOCKER_HOST`, `DOCKER_CONTEXT`, `DOCKER_CONFIG`, `DOCKER_CERT_PATH` and `DOCKER_TLS_VERIFY`. It also exports `dockerClientEnv()`.
  - `dispatchOnce` adds `--docker-env <json>` to the tool server's arguments.
  - `src/tool-server.ts` requires that argument. It refuses a name outside the list, and merges the values into its own environment before its first Docker call.

  New tests in `test/tool-server.test.ts`:
  - a probe stands in for `docker` and reports the `DOCKER_CONTEXT` it was given: `engine-a` with the argument, `unset` without it;
  - the refusal cases.

Not verified: a tool call against a non-default context on a real second engine, since this machine has one. `ARCHITECTURE.md` section 11 states the argument.
- **Finding 3: accepted and fixed, with the remediation quiescence gap the build record named.** New stage tests:
