## Method

Every cycle ran against a **scratch mirror** of the repository outside the
working tree, so no break ever touched the tree the plan was implemented in.
The mirror needs no `node_modules` — the suite imports nothing outside
`node:*` and `src/` — so a plain copy is a runnable repository.

Per cycle: apply the edits to the mirror, run the named test file with
`node --test --test-reporter=tap`, record whether the named test emitted
`not ok`, restore every edited file from a pristine copy, and compare the
restored file byte for byte. TAP rather than the default reporter because the
spec reporter's `✖` does not survive a Windows codepage round trip, and a
detector that silently never matches would report twenty-four false passes —
which is exactly what the first attempt did before the reporter was changed.

After the last cycle `diff -r pristine mirror` was empty.

## Two cycles that needed the plan's revision clause

The plan's Task 11 Step 1 says a break-it item is a hypothesis, and an
unreachable one is revised with the revision recorded. Two were.

**(k) `freezeProfile` re-reads the file instead of taking the parameter.** As
written this is unobservable: re-reading the same committed `governed.yaml`
produces the same configuration, so every test still passes and the cycle
would have proved nothing. What the guard actually protects is that the frozen
value is the caller's already-validated one — so the break became
"`freezeProfile` ignores the configuration it was handed and freezes its own",
which the profile round-trip assertion catches. The window between validation
and freeze remains an argument for the parameter, not a tested property.

**(w) the stage reads `VERIFY_COMMAND_TIMEOUT_SECONDS` instead of the frozen
value.** The real constant is 900 seconds, so the honest break would have hung
the suite for fifteen minutes. The cycle lowered the constant to 4 seconds in
the mirror *as part of the break*, and changed both the value passed to the
runner and the value named in the refusal. The test's
`/exceeded the 2-second ceiling/` assertion then failed against a message
naming 4 — which is the frozen-value guard, observed in four seconds.

## One cycle that hung rather than failed

**(n) the runner kills only the immediate child.** On Windows the child pid
belongs to the `cmd.exe` wrapper, so `child.kill()` leaves the node fixture and
its grandchild alive holding the stdout pipe, and `close` never fires. The test
did not fail — it hung, and the driver killed that run's process tree at 150
seconds. A guard whose removal makes a test hang instead of fail is still a
guard the test depends on, but it is worth knowing that this one is caught by a
hang rather than by an assertion. The duration assertion in the test would
catch a *slow* kill; only the timeout catches a kill that never completes.
