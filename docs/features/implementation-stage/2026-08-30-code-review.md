## Findings

**Finding 1 — a dangling symlink defeats the resolved-target checks, so the plan's "does not depend on the target's existence" guarantee is unmet**

- **Where:** `src/implementation-stage.ts` (the per-file checks at lines 418-447: `resolveExisting(target)` at 423, the `isPathInside` containment backstop at 424-426, the resolved-protected re-check at 433-436), built on `resolveExisting` in `src/scope.ts:23-39`; the symlink tests at `test/implementation-stage.test.ts:501-534`; the fixture's `symlink-design` mode at `test/fixtures/harness/emit-implementation-stage.mjs:114-124`, which creates the link target before the link.
- **Why it matters:** the plan's Task 7 step 5 states the refusals "fire on the resolved path and do not depend on the target's existence — `resolveExisting` resolves the link itself". `resolveExisting` walks with `existsSync`, which uses stat semantics and reports a dangling link as non-existent, so the walk skips the link and resolves its parent directory lexically. For a dangling symlink `src/alias -> src/agents` committed at the starting commit (a POSIX checkout), a proposed `add` of `src/alias/x.ts` passes the containment backstop and the protected re-check — both see the lexical path — and the apply's `writeFileSync` follows the link to its target, which may be a protected path (for example the run's own `docs/features/<slug>/design.md`) or outside the worktree. If Node's recursive `mkdirSync` on the link's dirname throws instead, the stage blocks with a misdiagnosed `patch write failed` rather than a refusal naming the resolved path. Either way the documented guarantee is not delivered, and the test never exercises the dangling case because the fixture creates the link target first — the assertion proves only the existing-target case.
- **Not reproduced:** the failure is POSIX-only and cannot be constructed on this machine: Windows junctions cannot dangle, and file symlink creation requires Developer Mode (the suite's own pre-flight at `test/implementation-stage.test.ts:513-528` skips it). Reachability: a POSIX checkout with `core.symlinks=true`, a committed dangling symlink at the approved starting commit, and an in-scope `add` proposal through it. Confirming it would require running the resolved checks against a dangling link on a filesystem that permits one. Verdict: PLAUSIBLE.

### Verdicts

- **Accepted — a dangling symlink defeats the resolved-target checks:** `runImplementationStage` now walks each component of the patch path with `lstatSync` and refuses any link whose target does not exist — `patch path <p> is a dangling link: its target cannot be resolved` — ordered before the existence checks, so a dangling file link under `add` can no longer have `writeFileSync` create the file at its (possibly protected) target, and a dangling directory link fails with a named refusal instead of a misdiagnosed `patch write failed`.
