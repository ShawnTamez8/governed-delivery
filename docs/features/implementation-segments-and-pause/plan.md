# Implementation Segments and Usage-Limit Pause Implementation Plan

**Status:** Shelved

Shelved 2026-10-12 by the operator: splitting oversized designs replaces segments (`docs/features/design-split-into-features/plan.md`); a pause on a usage-limit refusal remains a separate later decision.

**Goal:** Let the implementation stage build a plan larger than eight phases across several separately consented invocations on one run branch, up to a frozen backstop sized to what one code-review prompt can carry; let a provider usage-limit refusal end the invocation with every earlier phase kept and the run still continuable; and stop a build, with its true reason, as soon as it can no longer be reviewed, so neither a big plan nor a clock-driven refusal strands paid work without saying why.

**Source:** `docs/proposals/build-in-segments-and-continue.md` (written 2026-10-10). Operator statements: 2026-10-10, "If its over the limit, then we need to handle it" (a stop at spec review was rejected as blocking the same run sooner); 2026-10-11, "do both" in answer to whether to build segments, a design splitter, or both. Evidence: `docs/hazards.md` entries 18 and 20; `test/fixtures/recorded/crew-chatter-run-2-session-limit-refusal.json` (phase 6 of 6 refused after $9.63 of earlier phases); `test/fixtures/recorded/team-notes-run-8-session-limit-refusal.json`; `test/fixtures/recorded/plan-crew-chatter-run-2.json`; crew-chatter run 4's plan (86 task items against a frozen limit of 80), which is in the target repository but not yet in this one (Task 6 copies it); and two measurements of retained run branches made for this plan (Known blockers).

**Assumptions:**
- **"Do both" is a go-ahead to plan the proposal's direction, not an answer to its four numbered decisions.** This plan takes each decision as follows, and every one is listed under Open decisions for the operator to change before anything is built.
- **The reversal of the architecture is narrower than the proposal said.** `ARCHITECTURE.md` section 19 says an unsuccessful group "is never retried in that invocation". A pause ends the invocation, so that sentence stays true. What changes is section 19's "no general mid-stage recovery" and section 20's "a failed phase blocks the run and is not retried", and only for two named stops: the end of a segment, and a usage-limit refusal. Everything else stays terminal exactly as today: a scope violation, a refused patch, a dirty tree, a failed gate, an empty delivery, a timeout, any other non-zero exit, and a reply that is not valid JSON.
- **Numbers (mine, frozen at run start like every policy value).** Ten tasks per phase is unchanged. A new `implementationSegmentPhases` says how many phases one invocation builds; this plan seeds it at **8**, not the 3 the proposal suggested, because 8 is today's limit: every plan that is built in one invocation today still is, and only the plans that were refused behave differently. Three is a one-constant change if the operator prefers smaller bills per consent. `implementationMaxPhases` stays as the backstop that refuses a plan before any implementation spend, raised from 8 to **16** (160 task items). The 16 comes from the code-review prompt, not from the implementer: two measured builds put one review prompt at its 1 MiB ceiling at roughly 130 to 160 task items (Known blockers). It is a bound, not a promise; Task 5 measures the real prompt after every phase.
- **The phase-retry plan is not folded in.** `docs/features/implementation-phase-retry/plan.md` is `Reconciled` with the operator's own choices (2026-10-09) and covers a reply that is not valid JSON. Folding it would reopen those choices, and the two changes touch different branches of the stage: that plan changes the parse-failure branch, this one changes the dispatch-failure branch and the end of the phase loop. If both are built, the consent preview's ceiling for implementation becomes segment phases times attempts; the later one to be built makes that edit.
- **A pause is a state of the existing stage, not a new stage.** The stage row stays unfinished (an executing stage holds the store default `pending`, [Verified] by `src/dashboard/dashboard-model.js` `stageIsOpen` and the project learnings), the run stays `in_progress`, and the last audit event of that stage is a new `implementation.stage.pause`. No migration, no new table, no new column.
- **The run's snapshot phase for a paused run is `ready`**, with `workflowAction.group` `implementation`. No new `RunPhase` value. The dashboard's existing "READY TO RESUME" reading follows from `phase === "ready"` with no live writer ([Verified] by reading `statusPresentation` and `runRest`); it has not been looked at in a browser.
- **A crash is still not recoverable.** A process killed mid-phase leaves an unfinished stage whose last event is not a pause, which stays `interrupted_or_inconsistent` as today. Only a pause the stage wrote deliberately can be continued.
- **A refused attempt's reported cost is shown, not added to the run's recorded cost**, the same choice as `docs/features/usage-limit-refusal-summary/plan.md` (its open decision 1).
- **Guided mode does not loop.** A pause exits 3 with its message; the operator runs again and consents again.
- **The review-size stop blocks only on a measured fact.** A projection (linear, from the phases built so far) is shown at a pause as information and never blocks.

**Approach:** Add `implementationSegmentPhases` to the frozen policy and raise the backstop. Define the pause as one canonical audit summary with one parser and one finder in `src/handoff.ts`, shared by the stage and the run-state reader, so the two cannot disagree about what a pause is (the lesson of `itemText`). Let `dispatchOnce` carry a typed usage-limit signal on a failed result, built on `readUsageLimitRefusal` from the usage-limit plan, so the stage never parses text. In `src/implementation-stage.ts`, make the entry either start a fresh stage or continue a paused one; build at most one segment per invocation; at the segment's end, or on a usage-limit refusal that left the worktree untouched, write the pause event and return without completing the stage or blocking the run. A continuation refuses before any spend unless the worktree is on the run branch at exactly the head the pause recorded, clean, with the approved plan, spec, profile and age unchanged, and with the stage's `implementation.phase.apply` events agreeing with the pause. After every phase, build the real first code-review prompt for the work so far with the same builder code review uses and compare its size with the frozen prompt ceiling: over it, block now with the measured numbers instead of paying for phases that can never be reviewed; under it, say at each pause how full the prompt is projected to be. Teach `prefixAction`, `interpretBoundary`, `listRuns`, the `run` loop, the exit codes, the consent preview and the documents about the paused state. Tests run the real stage against the stand-in executor, replaying the recorded refusal streams, and every guard gets a break-it check.

**Hazards considered:**
- **Hazard 7** (retries that vary nothing): a continuation after a usage-limit refusal resends the phase prompt unchanged. That is not a retry of a bad output; the refusal was the clock, nothing in the prompt caused it, and the prompt is rebuilt from the same plan, scope and head. This is the one deliberate case of an identical resend, and Task 9 writes it into `ARCHITECTURE.md` beside the hazard-7 sentence. Every other failure keeps its terminal behaviour, so no retry that varies nothing is added.
- **Hazard 20** (one dispatch over a plan larger than one response): ten tasks per phase is unchanged, so no dispatch gets larger. The stored runs show the response cap is not what stops phases (largest response 98,218 of 128,000 tokens on Sonnet 5.5), recorded in the proposal. Only the spend backstop moves, and it now follows the next limit down the line.
- **Hazard 18** (delivery proven, correctness never inspected): its residual says a change whose diff, spec and plan exceed the prompt ceiling "is refused rather than reviewed in part". Segments make bigger builds reachable, so that refusal becomes the next wall. Task 5 states it earlier and with numbers; it does not weaken it, and nothing here lets a change through unreviewed.
- **Hazard 2** (discarded output is undiagnosable): the refused attempt's stream is already retained by `dispatchOnce` before any branch; the pause event names its reset time and reported cost so neither depends on opening the file. The review-size numbers are written to the audit chain at each pause.
- **Hazard 5** (completion without delivery): the implementation stage still passes only after the last phase, and writes its one gate event with the base before phase one and the final head. A paused stage has no gate event and no output reference, so verification, code review and delivery cannot run on a partial build; delivery coverage still reads the whole net range.
- **Hazard 6** (promises a later stage cannot keep): the consent preview says a segment may pause and that the next invocation asks again; it makes no promise that a run completes, and Task 5 refuses to keep paying for a build the review stage will refuse.
- **Hazard 4** (fixtures and code agreeing while both are wrong): expected reset times, windows and costs come from the two committed recordings, the 86-item plan from a committed copy of the real plan, review prompt sizes from the real prompt builder and `git diff` run independently of the stage, and the stand-in executor replays the recorded streams. Its state is the mode in its arguments, chosen by the test, never a counter that agrees with the stage.
- **Hazard 19** (an inactivity budget is a wall clock): a timeout is not a usage-limit refusal and still blocks. The pause recognises only the shape both recordings share.
- **Hazard 14** (independence that cannot be proven): this change loosens a state-machine invariant, so an independent review should be asked for after the build, in-session subagent or billed `/code-review ultra`, as a question for the operator rather than a silent choice.
- **Hard rules 3, 4 and 6:** no second schema or version field (the policy gains one field and earlier profiles are refused by name); one pause format with one parser and one finder, no framework; the segment size, the backstop and the prompt ceiling the guard compares with are frozen at run start and the stage reads `profile.policy`, never the constants.
- **Hazards 1, 3, 8, 9, 10, 11, 12, 13, 15, 16, 17, 21:** not weighed as design inputs. No prompt, schema, executable resolution, gate or stage sequence changes.

## Open decisions

1. **Segment size: 8 (this plan) or 3 (the proposal's suggestion).** Eight changes nothing for any plan that fits today. Three means every plan over 30 tasks needs a second consent but each bill is smaller. A frozen policy value either way.
2. **The backstop: 16 phases (160 task items).** Taken from two measured builds, so the basis is thin. Higher lets more plans past the pre-spend refusal and relies on Task 5 to stop an oversized build at the phase where the review prompt overflows; lower refuses earlier and more often.
3. **Fold the phase-retry plan in, or keep it separate (this plan).** If folded, a reply that is not valid JSON would retry in place and, when the frozen attempts are used up, either block (as that plan says) or pause.
4. **Whether a pause for an unreadable reply should exist once the retry plan is built.** Not decided here; today that failure blocks.
5. **Whether the refused attempt's cost should be recorded structurally.** Shared with the usage-limit plan's open decision 1; it needs a schema choice.
6. **Guided mode: exit 3 and ask again (this plan), or offer the next segment's consent in the same session.**
7. **The review-size stop blocks on a measured overflow and only warns on a projection (this plan).** It could instead pause and ask, since the operator might accept a build that code review will refuse for some other use of the branch.
8. **Whether code review should learn to review a large diff in slices**, which would lift the ceiling this plan works around. Not proposed here; the operator authorized `code_review` as it stands, and the alternative route, splitting the design, is in its own proposal.
